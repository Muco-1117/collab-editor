## 2. 负载模型与统计口径

`ConcurrentLoadTest` 对 10、50、100 个 WebSocket 客户端分别创建独立真实文档，并在同一房间内执行每客户端 20 条有效 `PUT`：

- 每个客户端最多保留 1 条未确认操作，收到与自身 clock 对应的 `applied` 后立即发送下一条；这是 closed-loop 持续并发，不是一次性管道突发；
- `clientId` 与 Lamport clock 的 replicaId 完全一致，counter 从 1 严格递增；
- 每条操作写入独立字段，避免合法的 LWW 淘汰被误计为丢失；
- 延迟从客户端调用 `send` 前开始，到收到自身对应 `applied` 为止；
- 吞吐为全部客户端开始发送至所有观察端收到最终 rev 的成功操作数/秒；
- 每个连接都必须观察到本轮全部唯一 clock 和连续 rev，数据库还必须满足日志增量、`operation_id` 唯一性与 seq 连续性；
- 50 客户端场景设置硬门限：P95 **严格小于 200 ms**。

100 人 presence 帧超过 Jakarta 测试客户端默认的 8 KiB 缓冲，因此负载夹具将客户端文本接收缓冲显式设为 256 KiB；服务端协议的 64 KiB 入站帧限制未变。

## 5. 结论

1. **收敛性通过**：8 副本、3 轮乱序回放的 `canonicalHash` 全部一致；
2. **可靠性通过**：10/50/100 三档均为零丢失、零重复，rev、唯一 clock、唯一 `operation_id` 与连续 seq 完全对齐；
3. **50 并发性能门通过**：最终 clean 轮 P95 为 125.50 ms，严格小于 200 ms；
4. **容量结果已留档**：100 客户端、2000 次写入完成 200,000 次广播投递，P95 为 389.59 ms；该档仅作本机容量观测，不设置超出需求的额外承诺。
